# Развёртывание после клонирования

Настройки конкретной машины и границы переноса: `docs/DEPLOYMENT_CONFIG.md`. Текущая лабораторная ВМ и конечный стенд — разные окружения; UUID/устройства/пути из `docs/VM_STORAGE.md` не копируются в новый deployment без адаптации.

## Границы этой версии

Это веб-часть Open WebUI с дополнительной страницей `/agent`, серверной проверкой личности и SQLite-хранилищем настроек. Базовый opt-in host-supervisor и lifecycle create/health/stop/start/restart/remove-retain приняты пользователем на ВМ для commit `4494d757`; см. `docs/verification.md`. Текущий локальный код добавляет отдельный purge, но он не включён в указанную VM-приёмку и не подтверждён на реальном XFS. Веб-only режим без override остаётся доступным. Gateway/chat, применение последующих draft changes, Telegram и LLM не подключены.

Веб-базис и отдельный лабораторный OpenClaw были приняты пользователем ранее; последующий персональный host-runtime также прошёл основной functional scenario на лабораторной ВМ по отчёту для commit `4494d7575b0c7534076684e6d8547477b527a42f`. Это не подтверждает перенос на новую машину, EDQUOT, полный API isolation или production readiness. Если сборка на новом стенде остановится на upstream-check — не отключайте его; выясните отличие образа от закреплённого исходника.

## Модель доставки

1. Локально изменяются исходники, тесты и документация.
2. После проверки и отдельного согласования репозиторий публикуется в GitHub.
3. На ВМ выполняются clone/pull, генерация местной `.env`, сборка и запуск Compose.
4. Пароли, `.env`, токены и Docker volumes в GitHub не передаются.

Ничего не публикуется автоматически. Для clone подставляется фактический адрес вашего репозитория вместо `<REPOSITORY_URL>`; этот placeholder не является настройкой runtime.

## Предпосылки

Команды ниже предназначены для Linux-ВМ с уже установленными Git, Docker Engine, Compose v2 и Python 3.12+. Установку этих средств согласовать отдельно. Docker на основной Windows-системе не нужен. Сборка скачивает закреплённый образ Open WebUI и образ Node для тестов; размеры и расход ресурсов пока не измерены. Локально npm/pip устанавливать не требуется.

## Первое развёртывание

```bash
git clone <REPOSITORY_URL> agent-platform
cd agent-platform
python3 scripts/init_env.py
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
```

`init_env.py` создаёт случайный ключ только локально и отказывается перезаписывать существующую `.env`. Не вставляйте значения ключей в чат или README. `docker compose config` без `--quiet` может раскрывать интерполированные секреты — такой вывод нельзя публиковать.

Compose по умолчанию публикует только `127.0.0.1:3000` на ВМ. Для доступа с основной машины используйте уже доступный SSH, например:

```bash
ssh -L 3000:127.0.0.1:3000 <VM_USER>@<VM_HOST>
```

Откройте в браузере `http://localhost:3000/agent`. Это соответствует `AGENT_PLATFORM_PUBLIC_ORIGIN` в сгенерированной `.env`. При смене origin/порта обновите настройку, иначе мутации будут отклоняться. Не публикуйте сервис в интернет для первого теста.

## Bootstrap и открытая регистрация

1. Первый аккаунт Open WebUI становится администратором. Создайте его самостоятельно через SSH-туннель, до открытия сервиса другим людям.
2. Upstream после первого аккаунта отключает signup в сохранённой конфигурации. В Admin Settings включите регистрацию и убедитесь, что роль новых пользователей — `user`, НЕ `pending` и НЕ `admin`.
3. В отдельном профиле/окне браузера создайте второго пользователя. Проверьте, что регистрация действительно открыта и новый аккаунт не получил admin.
4. `/agent` использует штатную сессию Open WebUI. Кнопка входа ведёт на `/auth?redirect=%2Fagent`. Штатный чат остаётся на `/`, однако без модели он не должен выдавать ответы.

Мы не копируем БД паролей, не создаём вторую систему регистрации и не выдаём собственные публичные тестовые токены.

## Что проверить после запуска

- `/health` отражает работоспособность Open WebUI, а не готовность OpenClaw/LLM.
- `/agent` показывает неподключённый runtime; нет выдуманных CPU/RAM или статуса running.
- Сохранение имени и инструкций переживает перезапуск сервиса.
- У второго пользователя свой пустой/отдельный набор настроек и журнал.
- API без сессии, с cookie без явного Bearer, с поддельным user-id заголовком или чужим Origin отклоняется.
- Подмена image, owner, mounts, privileges и Gateway URL не принимается.
- Секреты не попадают в ответы и журналы. При передаче диагностических логов всё равно просматривайте их: upstream-журналы не входят полностью в контроль нашего дополнения.

## Обновление

```bash
git pull --ff-only
docker compose build
docker compose up -d
```

Перед обновлением сохраняйте согласованную копию data-volume. В текущем проекте автоматическая резервная копия и миграционный rollback ещё не реализованы. Не используйте `docker compose down -v`, если хотите сохранить пользователей и настройки: флаг удаляет volume.
