# Этап 3 — контракт управления экземплярами (черновик)

**Статус: проектирование и реализация отдельного ядра начаты; стадия ещё не принята.** Этапы 1 и 2 остаются закрытыми. Установка пакетов, публикация, SSH и изменение работающего стенда не выполнялись и требуют отдельного согласования.

### Решения, уже подтверждённые пользователем

- Один экземпляр на пользователя в первой версии; остановленный экземпляр также занимает это место. Гонки создания должны исключаться серверной транзакцией/уникальным ограничением, не скрытой кнопкой.
- При удалении доступны оба режима: сохранить личные данные либо удалить их с отдельным явным подтверждением. Сохранённые наборы данных остаются привязанными к владельцу и учитываются по диску.
- Доступ только через кабинет: чат, разрешённые настройки и lifecycle. Прямой полный `operator.admin` Control UI пользователю не выдаётся; операторский доступ лаборатории не переносится в продукт.
- Предоставленные ресурсы ВМ: `free -h` — total 7.8Gi, available 5.5Gi, swap 5.1Gi; `nproc` — 8; корень `/dev/sda1` — Size 93G, Used 67G, Avail 22G, Use 76%. Это округлённый снимок из вывода пользователя, не точные байты для алгоритма допуска и не гарантия текущей нагрузки.
- LLM планируется на этой же ВМ. Предлагается общий модельный endpoint, к которому обращаются отдельные агенты, а не копия модели в каждом контейнере. Размер и резерв RAM/CPU модели пока не измерены; установка и скачивание модели не выполняются.
- Стартовый лимит агента — 2 GiB RAM по проверенному профилю, CPU — 1–2 по серверной конфигурации. Проверенный лабораторный default остаётся 1 CPU, изменение на 2 должно быть явным параметром профиля. PIDs пока сохраняются на уровне лабораторного профиля 256; это не новая системная настройка.
- Пользователь выбрал порог фактической занятости RAM или средней CPU от 50% с отдельным резервированием новых экземпляров. По его уточнению обязательное применение 50% относится к конечному стенду, не к текущему ограниченному лабораторному развёртыванию. Лабораторный профиль не должен выдавать наблюдение порога за его принудительное применение.
- Пользователь запросил 10–15 ГБ дискового пространства на экземпляр. Точное значение, единицы и механизм ограничения всех изменяемых данных ещё не утверждены. Это целевой диапазон, не реализованная квота и не гарантия уже выделенного свободного места.

Следствие: нельзя молча применять порог 50% к заполненности корневого диска — он уже заполнен на 76%. Дисковую политику необходимо отдельно согласовать; не удалять build cache или пользовательские данные автоматически.

## 1. Границы

Уже принято: открытая регистрация, персональные экземпляры OpenClaw, серверная проверка владельца, отсутствие прямого Docker API у браузера и агента, разделение пользовательских настроек и обязательных ограничений. Начальная реализация остаётся без LLM.

Предмет этапа 3: контракт web → supervisor, реестр экземпляров, шаблон исполнения, ресурсный допуск, повторные операции и восстановление. Реальная реализация lifecycle относится к этапу 4, Gateway/chat integration — к этапу 5.

## 2. Предлагаемая схема

```text
Браузер
  | штатная пользовательская сессия Open WebUI
  v
Web / control_plane
  | разрешённая операция + проверенный контекст владельца
  | отдельная служебная аутентификация
  v
Supervisor — единственный исполнитель lifecycle
  | внутренний реестр, очередь операций и резервов
  | формирование Docker-запроса по серверному шаблону
  v
Docker Engine на ВМ
  + экземпляр A: собственные state/workspace/auth, сеть, credentials
  + экземпляр B: собственные state/workspace/auth, сеть, credentials
```

Web не получает Docker socket. Supervisor — привилегированная граница доверия, а не «безопасный Docker proxy»: его компрометация рассматривается отдельно. Агенты не должны иметь доступ ни к его API, ни к socket, ни к секретам управления.

Лабораторный Gateway не становится экземпляром какого-либо зарегистрированного пользователя автоматически. Его данные и сопряжённые операторские credentials не копируются новым пользователям. Образ собирается один раз; клонирование/сборка OpenClaw при каждом создании не выполняется.

## 3. Служебная авторизация — предлагаемое решение, подлежит проверке

Для первой версии на одной ВМ предлагается отдельный локальный канал к supervisor с ограниченной сетевой/файловой достижимостью и выделенным служебным credential, отличным от Docker/Gateway/пользовательских токенов. Конкретный транспорт (Unix socket либо закрытый сетевой endpoint) и формат удостоверенного контекста должны быть зафиксированы до реализации, без заявления, что localhost означает доверие.

Web сначала проверяет штатную сессию, затем сам формирует actor ID. Внешние owner/user-id заголовки и поля body не используются как личность. Supervisor проверяет служебную сторону запроса, разрешённые типы операций и соответствие actor владельцу записи в своём реестре. Одной проверки службы недостаточно для доступа к произвольному экземпляру.

Доверенная web-служба технически способна заявить другого actor, если полностью скомпрометирована. Это явная граница первой схемы, не криптографическая end-to-end гарантия пользователя. До реализации выбрать проверяемую схему подписанного краткоживущего контекста либо документировать доверенную делегацию; не сочинять собственную криптографию. Credential, подпись или право записи в очередь не передаются в браузер или агент.

## 4. Реестр и источники истины

Текущий DraftStore хранит только один документ подготовленных настроек на пользователя. Он не является реестром контейнеров; его id нельзя молча трактовать как Docker container ID.

Предлагаемые сущности:

- `instances`: platform instance ID, owner ID, profile version, image ID, container ID, volume/network references, desired state, observed container state, gateway state, settings desired/applied revisions, creation/update times.
- `operations`: operation ID, actor ID, instance ID, action, idempotency key, canonical request fingerprint, status, stage, bounded error code, created/updated times.
- `reservations`: operation/instance reference, CPU/RAM/disk budget, state, lease/reconciliation metadata.
- `events`: actor/instance/operation IDs, event kind, result, time; без токенов, промптов, переписки и текста инструкций.

Для принятой модели одного экземпляра требуется уникальность owner среди не удалённых instances, включая creating и stopped. Сохранённые после remove данные описываются отдельным owner-scoped storage set, а не вторым активным экземпляром. Повторное создание после remove не получает чужой или случайно выбранный retained storage set.

Supervisor владеет записями исполнения и Docker-идентификаторами; web читает только разрешённое представление. Docker — источник фактического состояния контейнера; реестр — источник владения и утверждённого шаблона. Labels помогают сопоставлению, но сами по себе не устанавливают личность пользователя.

После рестарта нельзя объявлять все записи running: требуется reconciliation. Несоответствие шаблона, чужие volumes или неизвестный контейнер не исправляются автоматическим удалением данных.

## 5. Предлагаемый контракт операций

Публичные запросы остаются same-origin и проходят текущие проверки сессии, Origin, JSON и размера тела. Существующий `/me/actions` пока возвращает 503 — этот черновик не меняет поведение API.

Будущие запросы разрешают только operation, platform instance reference (если нужен), idempotency key и согласованные пользовательские настройки/их revision. Запрещены Docker JSON, owner ID, image, host paths, mounts, privileges, namespaces, обязательные policies и пользовательский Gateway URL. Откуда берётся instance reference и нужен ли он в `/me` — зависит от решения о числе экземпляров.

- `create`: проверить права, квоту и допуск, атомарно зарегистрировать операцию/резерв, создать ресурсы по шаблону, записать фактические ID, сообщить результат.
- `start`: проверять ресурсный допуск также для запуска остановленного экземпляра; остановка не обнуляет учёт диска и количества сохранённых экземпляров.
- `stop`: остановить только свой экземпляр, не удаляя данные.
- `restart`: сериализовать относительно других операций; политика временного резервирования уточняется вместе с допуском.
- `remove`: обязательный явный режим данных `retain` либо `purge`; режим purge требует отдельного подтверждения. Поле режима не является Docker JSON. Обычный запрос без явного выбора не должен незаметно удалять volumes.

Длительные операции возвращают подтверждение принятия с operation ID, не фиктивное завершение. Предлагается HTTP 202 для принятых задач; клиент получает owner-scoped статус. Создание считается успешным только после сверки реальных ресурсов, готовность Gateway отображается отдельно. Точные URI и JSON schema зафиксировать до этапа 4 после решений ниже.

Повтор одинакового idempotency key и канонического запроса возвращает ту же операцию; тот же ключ с другим запросом даёт conflict. Область ключа включает actor, action и target. Конкурентные операции одного экземпляра блокируются/сериализуются; общий резерв ресурсов обновляется транзакционно. Проверка свободной памяти до записи резерва сама по себе не исключает гонку.

Состояния операции: queued, running, succeeded, failed, reconciliation_required. Состояния контейнера/Gateway/модели не заменяются статусом операции.

## 6. Шаблон исполнения

Основа для первого профиля — проверенный baseline OpenClaw, но лабораторный Compose не переносится в многопользовательскую среду без адаптации.

- Образ закрепляется фактическим image ID из принятой сборки, а не только изменяемым тегом.
- На экземпляр — отдельные volumes, сеть и credentials; новые Gateway credentials генерируются отдельно.
- Порты персональных Gateway не публикуются всем пользователям автоматически; маршрутизацию определить на этапе 5.
- Нет Docker socket, host network, privileged и произвольных host mounts.
- Лимиты CPU/RAM/PIDs и диска обязательны как проектное требование; конкретные числа ещё не приняты для многопользовательского профиля.
- У лабораторного экземпляра уже проверены RAM/PIDs и writable rootfs. Это не готовый hardened профиль. Ужесточение UID/capabilities/rootfs проверяется отдельно на совместимость, не объявляется реализованным этим документом.
- Разрешённые персональные name/instructions уже существуют как draft; их применение и возможное расширение набора полей — отдельный согласованный контракт. Пользовательские instructions не являются обязательной доверенной policy.

Изоляция сети не должна случайно лишать агента всех полезных внешних инструментов: отдельно определить разрешённый выход и запрет доступа к управлению/другим экземплярам. Механизм disk quota зависит от хранения; обычный named volume не считать подтверждённой дисковой квотой без проверки реализации.

## 7. Допуск и ресурсы — открыто для согласования

Принят смысл порога: фактическая занятость RAM либо средняя загрузка CPU от 50% запрещает create/start на конечном стенде; новый экземпляр отдельно резервируется от переполнения ВМ. Сумма лимитов агентов не ограничивается половиной ВМ автоматически. Для лаборатории 50% пока наблюдается, а не навязывается; физические ограничения RAM/CPU/PIDs и защита от исчерпания диска не отменяются этим исключением.

Предлагаются два явно названных профиля: `lab` (одна лаборатория, порог 50% в режиме observe-only) и `final` (порог принудительный). Название профиля и активная политика видны оператору и в событиях. Профиль задаёт сервер, не пользователь. Это проект, не уже добавленный feature flag.

Предлагаемая точная семантика для спецификации реализации:

- RAM load = `(MemTotal - MemAvailable) / MemTotal`, без включения swap в физическую RAM.
- CPU load = средняя агрегированная загрузка всех доступных CPU за полное окно 60 секунд; не путать 100% одного ядра и 100% всей ВМ. При старте нет достаточного окна — метрика не готова, а не нулевая.
- В `final` равенство 50% уже даёт отказ. Результат метрик старше 10 секунд считается устаревшим. В `lab` эти условия пишутся как would-deny, а не скрываются.
- Независимая проверка бюджетов: резерв ОС/web/supervisor + резерв включённой модели + полные лимиты активных экземпляров + резервы pending операций + кандидат не превышают физический бюджет. CPU резервируется в согласованных CPU units, RAM — в байтах. Pending резерв переносится в active без двойного счёта.
- Дополнительный guard свежей доступной RAM и диска нужен для незарегистрированных нагрузок, например сборки образа; не суммировать наблюдаемое потребление управляемого экземпляра и его полный лимит в одном бюджете дважды.
- Профиль с включённой моделью требует явно заданного модельного резерва. Пока модель выключена, нулевой резерв допустим только при явно выключенной функции, а не как незаметный default для будущей LLM.

Окно 60 секунд, свежесть 10 секунд, бюджеты платформы/модели и пороги свободного диска являются техническими предложениями, ещё не измеренными на ВМ. Одновременную работу web, модели и нескольких агентов на указанной ВМ нельзя обещать до выбора модели и замеров.

Для обсуждения предлагается разделить:

1. Жёсткие бюджеты/резервы RAM и CPU для запущенных и создаваемых экземпляров, с отдельным резервом под ОС, web, supervisor и будущую модель.
2. Наблюдаемую загрузку: CPU за согласованное окно и RAM; свежесть данных проверяется. Диск — отдельный порог свободного места и учёт сохраняемых данных.
3. Ограничения каждого работающего экземпляра и частоты регистраций/lifecycle, а не только однократный порог создания.

Нельзя суммировать всю наблюдаемую RAM уже учтённых контейнеров и их полные резервы дважды. В окончательном контракте определить источник/единицы каждой метрики, базу 50%, граничное равенство, окно CPU и атомарный расчёт нового резерва. При отсутствии достоверных метрик предлагается fail-closed для create/start, но stop и безопасное обслуживание должны оставаться доступны.

Приняты 2 GiB RAM и диапазон 1–2 CPU на экземпляр; исходный профиль — 1 CPU / 256 PIDs. Реальные мощности ВМ и размещение LLM уже получены от пользователя. Остаются численные резервы платформы/модели и проверка дискового механизма. Порог 50% не является полной защитой от DoS.

### Диск: отдельный незакрытый технический вопрос

Цель — 10–15 ГБ на экземпляр, включая изменяемый слой и личные volumes; общие read-only слои образа не выдаются за личный свободный диск. Настройка максимального размера и резерв реально свободного места — разные свойства. Логи контейнера и сохранённые после remove наборы данных также требуют отдельного ограниченного учёта.

Нельзя объявить лимит named volume работающим простым добавлением значения в JSON шаблона: нужен проверенный механизм хранения/квот на реальной файловой системе Docker. Возможность конкретного драйвера не утверждается без проверки документации выбранной версии и фактического хранения на ВМ.

Получены read-only сведения пользователя: `Driver=overlay2`, `DockerRootDir=/var/lib/docker`; в полном `findmnt` корень `/dev/sda1` имеет тип `ext4`, опции `rw,relatime,errors=remount-ro`, отдельного mount для DockerRootDir в выводе нет. Квоты этим выводом не подтверждены. Ошибка адресного запроса вызвана колонкой `OPTION`; правильное имя `OPTIONS`. Повторять весь сбор информации из-за этой опечатки не нужно.

Проверка первичной документации Docker: для overlay2 параметр размера `--storage-opt size=...` требует backing filesystem XFS с pquota; к текущему ext4 этот способ не применим. Личные volumes находятся вне writable layer, поэтому ограничение одного слоя контейнера само по себе не является общей квотой данных. Источники для технической проверки: Docker Docs, `docker container run`, раздел `Set storage driver options per container`; Docker Docs, `Volumes`, разделы lifecycle и block storage.

Предлагаемый вариант для конечного стенда — выделенное хранилище личных данных с поддержанными и испытанными project quotas, не переустройство текущего корневого раздела работающей ВМ. Это предложение, не согласие на добавление диска, форматирование, изменение ФС или миграцию. Использование квот ext4 на существующем корне потребовало бы отдельного выяснения filesystem features и плана безопасного включения; отсутствие quota-флагов в findmnt не заменяет эту проверку.

Отдельный файловый disk image/loop device — только возможный лабораторный эксперимент, не выбранный default: Docker Docs прямо предупреждает, что пример не является общей рекомендуемой практикой. Нужны управление монтированием и восстановлением после reboot, учёт внешнего файла, прав и безопасной очистки. Создание образа, mount и форматирование без отдельного согласования запрещены.

До выбора и испытания backend нельзя выдавать 10–15 ГБ за реализованную hard quota. Для целевого ограничения всех постоянных записей также потребуется решить судьбу writable layer: например, отдельным испытанием read-only rootfs и разрешённых writable путей, плюс ограничением логов/временных данных. Квота только state/workspace не доказывает ограничение всей записи агента.

Следующее решение — согласовать выделенное хранилище с квотами для конечного стенда либо отдельно согласованный лабораторный режим без заявления жёсткой дисковой квоты. Никакие пакеты, mount options, дисковые образы и данные на ВМ не изменялись.

Предложение против обхода через remove/create: общий owner-scoped бюджет данных покрывает активный экземпляр и все retained storage sets. При исчерпании бюджета предлагается восстановить свои данные либо явно подтвердить удаление выбранного набора; автоматического purge нет. Точное правило общего бюджета ещё должно войти в утверждённую спецификацию.

## 8. Удаление и сбои — проектные предложения

Пользователь выбрал оба варианта удаления: сохранить данные либо удалить их после отдельного подтверждения. В интерфейсе безопасный исходный выбор — retain, но окончательный запрос содержит явный режим. Сохранённые volumes занимают диск и входят в квоты. Повторное подключение сохранённых данных допускается только тому же владельцу после проверки версии/политики; удалённый instance ID не переиспользуется как чужой объект.

Purge — отдельная подтверждённая стадия операции, не неявный побочный эффект удаления контейнера. Подтверждение привязывается к владельцу, экземпляру, версии/набору данных и режиму; изменение выбора требует нового подтверждения. Удаление Docker volume не заявляется как гарантированное необратимое стирание всех копий и резервных снимков. Срок хранения retained данных ещё не принят, автоматическое удаление по таймеру не включается.

После частичного create supervisor сверяет реальные ресурсы с operation ID. Удаляет только доказанно принадлежащие своей незавершённой операции новые ресурсы; чужие/ранее сохранённые данные не трогает. Резерв не освобождается по одному таймауту, если контейнер мог продолжить запуск: сначала reconciliation. Секреты и Docker-ошибки не возвращаются в браузер без безопасного преобразования.

## 9. Проверки до приёмки реализации

- Личность отсутствует/подменена; чужой instance и operation ID; скомпрометированный внешний user-id header не даёт доступ.
- Supervisor без служебного credential недоступен, replay/срок действия проверяются согласно выбранной схеме.
- Неизвестные инфраструктурные поля и произвольные адреса/команды отклоняются.
- Повтор create не дублирует контейнер; два конкурентных create не обходят квоту и резерв.
- Метрики отсутствуют/устарели, порог равен 50%, новый экземпляр не помещается, CPU-скачок, нехватка диска.
- Сбой до/после Docker create/start, до записи ID и до ответа клиенту; восстановление не создаёт дубль и не удаляет личные данные.
- Restart supervisor/web/ВМ, рассогласование контейнера и реестра, чужие ресурсы с похожими именами.
- Remove по согласованной политике, сохранение и owner-scoped повторное подключение данных, отдельный purge.
- Настоящие проверки двух экземпляров: файлы, credentials, сетевые обращения и управление; наличие двух имён контейнеров не является результатом такой проверки.

Эти проверки пока только спроектированы, не выполнены. Unit fixtures не заменяют проверку настоящего Docker на ВМ.
