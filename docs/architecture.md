# Архитектура первой веб-части

## Выбор основы

Используется закреплённый prebuilt Open WebUI v0.12.5-slim. Его регистрация, вход, роли и чат сохраняются. Вместо нового frontend build и переписывания аутентификации добавляется небольшая самостоятельная страница `/agent` в том же HTTP-сервисе и same-origin API. Полное встраивание кнопки в Svelte sidebar пока не сделано: страницу открывают по прямой ссылке, из неё есть переходы к штатному входу и чату.

При Docker build исходный `main.py` сверяется с SHA256 исследованного commit и добавляется подключение router до SPA mount. Несовпадение версии останавливает сборку. Брендинг и штатные исходники Open WebUI не переименовываются.

## Поток данных

```text
Браузер /agent
  -> Authorization: Bearer <штатная human session>
  -> Open WebUI get_verified_user
  -> обязательная проверка role/auth_type/token type
  -> owner-scoped SQLite draft settings / events
```

`control_plane` не знает паролей и не устанавливает личность самостоятельно. Браузер не передаёт owner_id. API не принимает произвольный адрес Gateway и вообще не выполняет исходящих запросов. Секрет сессии никогда не попадает в URL.

В этой версии не используется подписанный upstream identity JWT: он может понадобиться позднее для chat routing, но для встроенного API доступен штатный серверный UserModel.

## Реальное и неподключённое

Реально реализованы хранение подготовленных настроек, ограничение полей, optimistic revisions, разделение данных в запросах, ограниченный журнал и отдельная страница. Отдельно подключён opt-in host-runtime для provisioning и Docker lifecycle; его функциональная приёмка на ВМ по пользовательскому отчёту описана в `docs/verification.md`. Сохранение draft после создания по-прежнему не применяет изменения к уже работающему OpenClaw; Gateway, чат, модель и Telegram не подключены.

## Безопасность нового API

- Только явный session Bearer; cookie-only и API keys для управления запрещены.
- Штатная подпись/срок/отзыв сессии и загрузка пользователя — ответственность Open WebUI; наш код повторно ограничивает активные роли и human session.
- Изменения только через PUT/POST с JSON, проверкой Origin/Fetch Metadata и лимитом 64 KiB; повторяющиеся JSON-поля отклоняются.
- Owner определяется сервером. Даже admin не получает через `/me` чужие личные настройки.
- SQL параметризован, CAS-update выполняется в транзакции. При конфликте 409 данные не перезаписываются.
- В журнале только код события и время; текст инструкций туда не копируется. На владельца сохраняется не более 100 событий, API выдаёт последние 25.
- Страница использует внешние локальные CSS/JS и безопасное отображение пользовательского текста. Никаких CDN, сторонних аналитических скриптов или fake ответов.
- Docker socket и host network не выдаются вебу/агенту. Пользовательский отчёт подтверждает фактические основные Docker limits для проверенного контейнера; это не означает, что все ограничения/изоляция прошли обходные security-тесты.

Это НЕ аудит всей поверхности Open WebUI: новые ограничения не заменяют проверку его остальных endpoints, XSS/CSRF, регистрационных лимитов, плагинов, загрузок и сетевых функций. До такой проверки предусмотрен только локальный вход через SSH-туннель.

## Модель данных

Текущая локальная реализация хранит один документ настроек на пользователя в DraftStore, а отдельный RuntimeStore ведёт один активный экземпляр на владельца и retained disk после remove. Это не multi-instance-per-owner. Отдельный owner-scoped purge retained dataset добавлен в текущей локальной копии и не принят на ВМ; переподключение retained storage отсутствует. Допустимые поля формы — name и instructions; сохранение draft не означает применения настроек в уже созданном агенте.

## Исследованные первичные источники

- Open WebUI commit `f7ac7ee10962ddec0017f5c29b6740d9b9c5faca`: `utils/auth.py`, `routers/auths.py`, `utils/headers.py`, `main.py`, Dockerfile.
- OpenClaw theory commit `7c12438929e5d198616fe8f602d896e011647d39`: Gateway RPC, config read-only guard, Docker bootstrap и Telegram transport.
- Принципиальные ограничения OpenClaw: WS pairing не заменяется shared token; read-only касается всего config; startup entrypoint запускает Doctor; HTTP chat не является supervisor API.

Исследование исходников не заменяет интеграционные тесты. Полные исследовательские артефакты хранятся отдельно в локальном scratch, не входят в runtime и не обязательны для clone/build.
