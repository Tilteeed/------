# Настройка конкретной машины и перенос стенда

## Два разных окружения

Текущая лабораторная ВМ пользователя и конечный стенд — **разные машины**. UUID, устройства, mountpoints, объёмы дисков, RAM/CPU, адреса и результаты испытаний текущей ВМ не становятся конфигурацией конечной машины автоматически.

`docs/VM_STORAGE.md` — свидетельства только лабораторной ВМ, а не универсальная инструкция монтирования. Строку fstab из него нельзя копировать на другую машину без проверки и замены параметров. Даже одинаковая метка тома не подтверждает нужную идентичность.

Переносится проект и утверждённые политики; окружение подготавливается и проверяется отдельно. Сам запрос на переносимость не разрешает форматирование, миграцию данных или установку ПО.

## Какие числа относятся к окружению, а какие — к политике

- UUID, пути, адреса и измеренные мощности машины определяются для каждого deployment. Лабораторные ресурсные defaults не являются универсальным профилем.
- **Порог 50% — общее решение пользователя для проекта**, сохраняемое при смене машины. Он не является характеристикой ВМ и не должен становиться произвольно редактируемым пользовательским параметром. Существующее лабораторное наблюдение `would_deny` и принудительный отказ в `final` различаются режимом применения, не величиной порога; в этом изменении режимы не менялись.
- Окно CPU 60 секунд и свежесть метрик 10 секунд — технический baseline текущей политики. При реализации coordinator предусмотреть централизованную версионированную политику для этих параметров с валидацией. Сейчас такого загрузчика нет; само наличие констант не является ошибкой переносимости.
- Ограничения схем API, длины полей и правила idempotency — правила приложения, не host-настройки. Не выносить все числовые константы в `.env` ради формальной настраиваемости.
- Обязательные ограничения задаются только доверенной платформой, а не пользователем/агентом. Нужные параметры должны быть корректны и подтверждены проверками; иначе будущие create/start отклоняются до записи, без небезопасных defaults. Это требование к интеграции, не утверждение о уже подключённом runtime.

## Где менять и смотреть сейчас

| Что | Где смотреть/менять | Правило для новой машины |
| --- | --- | --- |
| Порт веба | `WEB_PORT` в локальной `.env`; описание в `.env.example` | Выбрать доступный порт; проверить фактическую публикацию Compose. |
| Публичный origin кабинета | `AGENT_PLATFORM_PUBLIC_ORIGIN` в `.env` | Указать фактические схему, hostname и порт доступа, не копировать лабораторный localhost без проверки. |
| Память/CPU веба | `WEB_MEMORY_LIMIT`, `WEB_CPU_LIMIT` в `.env` | Подобрать по ресурсам и замерам новой машины. |
| Ключ веб-сессий | `WEBUI_SECRET_KEY` в `.env` | Для независимого нового стенда сгенерировать локально через `scripts/init_env.py`; не копировать лабораторный секрет. Генератор не перезаписывает существующую `.env`. |
| Начальная установка веба | `docs/deployment.md`, `compose.yaml` | Инструкция относится к веб-части, не к готовому персональному provisioning. |
| Лабораторный OpenClaw | `lab/openclaw/README.md`, локальная конфигурация лаборатории | Не переносить автоматически лабораторные volumes, pairing и credentials пользователям конечного стенда. |
| Факты текущей ВМ | `docs/VM_STORAGE.md`, исторические снимки в `docs/STAGE3_CONTRACT.md` | Использовать как свидетельства/пример, не как defaults. |
| Стадии и приёмка | `docs/ROADMAP.md`, `docs/verification.md` | Различать проверку текущей ВМ и приёмку нового окружения. |

Реальную `.env` и credentials не коммитить. Не редактировать код вместо локальной конфигурации только ради смены машины. Перенос существующих пользователей, БД, ключей и данных — отдельная миграция, не обычная установка независимого стенда.

## Что потребуется для будущего supervisor/storage backend

**Загрузчик конфигурации storage backend ещё не реализован.** Следующая таблица — требования к будущему deployment-профилю, а не уже поддерживаемые переменные окружения или готовая схема JSON. Сейчас чистые policy/registry получают ресурсы и capacity snapshots аргументами от вызывающего доверенного кода; это не автоопределение параметров машины.

| Параметр окружения | Источник на новом стенде | Что не делать |
| --- | --- | --- |
| Путь к хранилищу и ожидаемая идентичность ФС | Проверенные администратором mountpoint/UUID нового тома | Не вшивать UUID текущей ВМ в Python, Compose, shell или defaults. |
| Storage backend и требуемый тип ФС | Реально подготовленный и поддержанный backend с испытанными квотами | Не считать XFS обязательным для любой машины или любую другую ФС уже поддержанной. Несовместимый профиль должен блокировать provisioning. |
| DockerRootDir и storage driver | Фактическая диагностика Docker на целевой машине | Не приравнивать личный том данных к backing filesystem Docker. |
| Ресурсы хоста, системные резервы и резерв модели | Свежие метрики, замеры модели и администраторский профиль | Не копировать RAM/CPU/free disk из документации лабораторной ВМ. |
| Лимиты агента и дисковая квота | Утверждённый серверный профиль с явными единицами | Не превращать диапазон 10–15 ГБ в скрытый default или доказанную квоту. |
| Пути БД/очереди, служебный endpoint и credentials | Локальная конфигурация доверенной службы | Не принимать их из браузера или пользовательских настроек агента. |

При реализации рядом с чтением параметров и машинно-зависимыми проверками добавлять пояснение: откуда параметр, кто его задаёт, единицы, обязательность, допустимый default и отказ при неверной настройке. Установить одно определённое место загрузки deployment-профиля и описать его здесь; не разбрасывать одинаковые параметры по коду и документации.

## Проверки перед допуском на новом стенде

1. Администратор задаёт ожидаемые storage identity/path **этой** машины. Нельзя автоматически принимать наблюдаемый UUID за ожидаемый при каждом старте: это отменяет проверку идентичности.
2. Supervisor сверяет фактический mount, идентичность, тип ФС и работоспособность выбранного quota backend с локальным deployment-профилем. Само существование каталога не является успешной проверкой.
3. Отсутствующая или несовместимая конфигурация — отказ до записи и provisioning, без fallback на корневой диск и без автоматического форматирования/включения квот.
4. Подтверждаются конкретные per-instance лимиты, owner isolation, сохранение данных и восстановление после согласованных перезапусков. Результаты лабораторной ВМ не выдаются за результаты новой машины; при этом они не обнуляют уже принятую лабораторную работу.

В unit-тестах использовать явно синтетические устройства/UUID/ресурсы, не предполагать наличие лабораторного диска. Реальные host-проверки отделять от переносимых unit-тестов.
