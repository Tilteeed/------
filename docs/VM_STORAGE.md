Конечный стенд будет на другой машине.** UUID, устройства, пути и размеры ниже — свидетельства этой ВМ, не универсальная конфигурация и не значения для хардкода. Для новой машины нужно определить и задать собственные параметры: см. `docs/DEPLOYMENT_CONFIG.md`.

Пользователь самостоятельно подготовил новый диск и XFS для данных агентов. Это текущая основа проектирования storage backend. Подготовку корневого ext4 больше не считать выбранным следующим шагом.

| Параметр | Значение |
| --- | --- |

| Project quota accounting | `ON` по `xfs_quota -x -c 'state -p'` |

| Свободное место в присланном снимке | `49G`, общий размер ФС `50G` по `df -hT` |

UUID и точка монтирования являются ожидаемой идентичностью только этой лабораторной ВМ; имя устройства может измениться после перестановки дисков. На другой машине ожидаемая идентичность задаётся её deployment-профилем. Размеры и свободное место — снимок, не постоянно гарантированный ресурс.

## Принятые проверки профиля на Linux-ВМ

Пользователь предоставил выводы настоящего запуска: локальный профиль `lab-v1` / `mode=lab` принят CLI; неизменённый example отклонён с exit 2; на Linux прошли 37 supervisor- и 15 storage-тестов предыдущего среза. В этом профиле явно заданы `ram_bytes=2147483648`, `cpu_millicores=1000`, `pids_limit=256`, **`disk_bytes=10737418240` (10 GiB)**. Это выбранные значения именно этой ВМ, не defaults конечного стенда и не уже установленная квота.

Новый вывод `findmnt --mountpoint /srv/agent-data` подтверждает точку монтирования, XFS и UUID из таблицы; `xfs_quota state -p` вновь показывает Accounting/Enforcement ON. Колонка OPTIONS в присланном табличном выводе обрезана; состояние quota подтверждается отдельной командой, не угадыванием скрытых символов. В этом фрагменте нет проверки записи 10 GiB настоящим OpenClaw или нового первичного результата малой пробы 100 МиБ.

Последний показанный режим файла `supervisor/deployment.local.json` — `0644`, владелец/группа — учётная запись оператора этой ВМ; первоначальный `chmod 600` затем отменён командой `chmod 644`. CLI проверяет содержимое, а не доверенность владельца/родительских каталогов. Самостоятельно права помощник не менял. Текущий профиль не содержит credentials; подключение службы и её безопасный доступ к конфигурации остаются отдельной задачей.

Успешная проверка fstab не подменяет проверку фактического монтирования после reboot; отдельное сообщение о последней приведено ниже.

## Что подтверждено и что ещё нет

- По отчёту пользователя о проверке commit `4494d7575b0c7534076684e6d8547477b527a42f` для нового работающего экземпляра подтверждены XFS Project ID `2` и назначенная/readback квота 10 GiB. Это свидетельство конкретного экземпляра этой ВМ; первичные командные выводы в этом файле не приложены.
- Фактический отказ записи при достижении квоты (`EDQUOT`) на экземпляре OpenClaw не проверен. Readback лимита не доказывает kernel enforcement и полный охват всех путей записи.
- Связывание state/workspace с XFS подтверждено отчётом для текущего экземпляра; миграция существующих контейнеров/данных и перенос DockerRootDir не подтверждены.
- Ранее исследованный `/dev/sda1` остаётся исторической диагностикой корневого ext4. Старый `lab/storage/inspect_ext4.py` исследует DockerRootDir, а не произвольный новый том, поэтому его нельзя выдавать за проверку `/srv/agent-data`.
- Квота личных данных сама по себе не подтверждает охват writable layer и внешних логов Docker; ограничение всего изменяемого объёма требует отдельной проверки.

## Обязательные проверки будущего storage backend

1. До любой записи/создания экземпляра проверить фактический mount/UUID/тип ФС по deployment-профилю конкретной машины. Для этой лабораторной ВМ ожидаются `/srv/agent-data`, XFS и UUID из таблицы; для конечного стенда значения определяются заново. Проверки одного существования каталога недостаточно; путь не должен оказаться обычным каталогом на `/`.
2. Проверить актуальное состояние quota accounting/enforcement и соответствие назначенного project ID утверждённому экземпляру/владельцу.
3. При отсутствии ожидаемого mount, другой идентичности или неработающих квот — отказ до создания/записи. Не делать автоматический fallback на корневой ext4. Наличие `nofail` в fstab не является разрешением supervisor продолжать без тома.
4. Отчёт `2afe2b5` подтверждает для двух тестовых instances отдельные project IDs/quota и readback 10 GiB; для временного test set дополнительно подтверждена запись marker на XFS. На изолированных synthetic data и только по согласованному сценарию отдельно проверить отказ записи при превышении hard limit и охват нужных путей. Не проверять переполнение текущих пользовательских данных.
5. Для disposable test set отчёт `2afe2b5` подтверждает реальную XFS запись marker, remove-retain и purge/project quota release. Этот тест завершён, его dataset очищен; не использовать его как restore target. На конечном продукте отдельная restore операция должна быть испытана только на новом owner-approved retained test dataset после явного согласия.

Read-only mount/UUID/XFS/quota-state guards были реализованы как отдельный preflight. Отчёт `2afe2b5` подтверждает XFS write, remove-retain и purge/project release на disposable test set; пользователь сообщил, что dataset удалён после теста. EDQUOT, adversarial race testing и восстановление supervisor после restart остаются открытыми. Restore нового локального кода на ВМ не проверялся. Не выполнять изменяющие ФС действия по этой инструкции без отдельного согласования.

## Граница разрешений

Подготовку диска и fstab выполнил пользователь. Помощник только сохранил предоставленные сведения. Это не разрешает повторное форматирование, remount, изменение fstab, миграцию, назначение новых квот или удаление данных. Следующие изменяющие хранилище операции согласовываются отдельно.
