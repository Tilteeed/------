# Однократное восстановление после reboot

## Область и статус

Локальный путь `serve()` → `RuntimeService.reconcile(boot=True)` → ticks `UnixServer.service_actions()` подключает отложенное восстановление. Это не watchdog и не повторный общий `reconcile()`. Реальный Linux/systemd/Docker reboot ещё не проверен. Службы, Docker, XFS, пользовательские данные и GPU-сервер в ходе разработки не менялись.

## Что считается reboot

Supervisor читает фиксированный `/proc/sys/kernel/random/boot_id`. `RuntimeStore.claim_boot_recovery()` сохраняет boot ID в отдельной строке `boot_recovery` под SQLite writer transaction с `synchronous=FULL` **до** автоматического запуска Docker. Таблица создаётся при первом вызове на корректной runtime DB; существующий desired-state migration этим не заменяется. На рабочей пользовательской БД новая процедура не выполнялась.

- Первая встреча boot ID только устанавливает baseline: неизвестно, произошла ли сейчас загрузка или установка новой версии посреди uptime. Автоматического запуска в этот раз нет; нужные экземпляры запускаются явным пользовательским действием.
- Изменившийся boot ID разрешает один startup-pass. Тот же boot ID после restart Supervisor ничего повторно не запускает.
- Сбой после фиксации claim не возвращает право запуска при рестарте службы. Неподнятые экземпляры требуют ручного действия; это намеренное fail-closed поведение.
- Не удалять boot marker/SQLite и не менять binding ради повторной попытки.

## Boot-кандидаты и запуск

`RestartPolicy=no` сохраняется. Сначала восстанавливается и проверяется firewall для обнаруженных управляемых сетей. Отсутствующие контейнеры не создаются. Кандидат должен быть активен, initialized, иметь persisted `desired_state=running` и тот же полный Gateway Docker ID, что записан в runtime journal. Для `agent_proxy_v1` проверяется существующий Sidecar и фиксируется его полный Docker ID. Неизвестные/частичные спецификации, пара с отсутствующим или неподтверждённым Sidecar, ошибочная сеть/receipt не получают права запуска.

Здесь `desired_state` — сохранённое намерение запуска, а не доказательство состояния процесса в последнюю секунду перед отключением. Snapshot точных Docker IDs пары делается в initial boot-pass и служит независимым ожидаемым значением при повторной проверке после прогрева. Он не переносится в новый процесс Supervisor: claim уже consumed, поэтому при прерывании нужен ручной запуск.

Немедленный запуск при уже свежих метриках также привязан к точным IDs. В отложенный набор попадают **только** экземпляры, у которых единственная причина admission отказа — неполное CPU-окно. Storage/model-policy/identity failure не маскируется как ожидание метрик.

Основной server-loop проверяет готовность без sleep/join и без ожидания занятой lifecycle lock. Нужны CPU-окно не менее 60 секунд и доверенный sample не старше 10 секунд. Ожидание заканчивается через 180 секунд от startup-pass; это технический тайм-аут ожидания, не новый ресурсный лимит. Он не является общим тайм-аутом уже начатых Docker операций: у них свои transport timeouts.

Перед единственной попыткой весь кандидатный набор изымается из очереди. Для каждого заново проверяются:

1. Active/desired state, owner/settings/storage binding, выбранная модель и отсутствие незавершённой Sidecar migration.
2. Firewall restore/readback и принадлежность экземпляра проверенному inventory.
3. Точные Gateway **и** Sidecar IDs, Docker spec и сети.
4. Идентичность хранилища и действующая квота, свежий resource admission.
5. Управляемая model policy и отдельный Ollama route gate, если Ollama включена.
6. Identity-bound старт и postconditions. Все boot-наблюдения, включая startup-pass и проверку после запуска, используют read-only `inspect`/`control_ui_target`: они не подключают WebUI к сети и не останавливают одноимённые замены. Post-start наблюдение дополнительно получает оба ожидаемых полных ID. При неоднозначном результате containment адресуется только ранее зафиксированным полным IDs; `stop_bound(False)` явно регистрируется как неподтверждённое containment.

Явная lifecycle action или административная смена модели отменяет соответствующий pending boot-кандидат. Ошибка попытки, последующее падение, stop/remove/replacement не создают второй попытки. Смена модели восстанавливает только экземпляры, которые сама остановила живыми; посторонние ранее упавшие экземпляры общим reconcile не перезапускаются.

## Доверенная граница

Lifecycle lock сериализует только сотрудничающие операции Supervisor. Root и независимые операторы Docker Engine входят в доверенную административную зону и не должны параллельно заменять контейнеры/сети/файлы. Полные ID не позволяют принять одноимённую замену за прежний объект, но не превращают root в недоверенного пользователя. Шаблон systemd-unit сам по себе не установлен и не доказывает порядок загрузки. Docker не должен стартовать пару сам до firewall readiness.

## Проверки

Локальные тесты используют синтетический Engine/metrics/storage, а epoch-тест — настоящую временную SQLite с reopen. Они проверяют единичность попытки, stop/remove/оба replacement IDs, firewall/quota/admission failure, stale metrics/timeout/shutdown, отсутствие повторного старта после crash и сохранение claim при restart службы. Они **не** подтверждают Linux ioctl, Docker packet path, настоящий XFS или фактический systemd startup order.

После отдельного разрешения достаточно одной целевой серии на disposable Linux/XFS/Docker стенде, без повторения прежней Stage 3:

- Два экземпляра: один desired-running, второй явно stopped; сохранить полные IDs обоих контейнеров и synthetic marker/project identity до reboot.
- После reboot убедиться, что ни один контейнер не начинал сетевую работу до firewall readback; после CPU warmup поднялась только прежняя desired-running пара с теми же IDs, квотой и marker.
- Обычное аварийное завершение Gateway после успешного восстановления, затем restart Supervisor в том же boot: автоматического старта нет.
- В отдельном повторе холодного сценария до warmup выполнить stop либо заменить Sidecar; кандидат не запускается. Замена выполняется только на disposable экземпляре, без пользовательских данных.
- Несовпадающий firewall/route receipt или storage identity блокирует запуск. Не ослаблять проверки и не удалять БД для завершения сценария.

Нужные системные изменения и адреса/rules apply/rollback согласовываются перед реальными испытаниями; этот документ не разрешает их выполнение.
