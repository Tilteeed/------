# Функциональные требования и границы проекта

## Согласованный замысел

- Открытая регистрация без одобрения администратором.
- Персональные экземпляры OpenClaw с индивидуальным состоянием и рабочими данными.
- Работа через браузер с сохранением необходимых штатных возможностей агента.
- Пользовательские настройки и собственный Telegram-бот в разрешённых пределах.
- Создание, просмотр состояния, запуск, остановка, перезапуск и удаление экземпляра.
- Владелец экземпляра не получает право отменить обязательные ограничения платформы.
- Управление Docker находится в доверенном компоненте, недоступном агентам и прямым пользовательским запросам.
- Начальная работа без LLM. Готовность Gateway и модели отображается раздельно.
- ВМ создаёт пользователь самостоятельно; развёртывание на ВМ — после предоставления и согласования доступа.
- Порог занятости половины ресурсов для отказа новым созданиям предложен пользователем. Это контроль допуска, не полная защита от DoS.

## Порядок

1. Исследовать выбранную версию OpenClaw и точки интеграции.
2. Проверить OpenWebUI как возможную основу; не выбирать самописный кабинет заранее.
3. Согласовать необходимые зависимости и устанавливать их изолированно.
4. Реализовывать работоспособные этапы и явно обозначать неподключённые компоненты.

## Требования к границам безопасности

### Веб

- Проверять права на конкретный экземпляр при каждом запросе.
- Определять пользователя по серверной аутентификации, не по полю формы.
- Использовать штатную аутентификацию проверенной основы вместо собственной криптографии и системы паролей.
- Проверить модель сессий выбранной основы и соответствующие меры против CSRF; не предполагать автоматически cookie-сессии или bearer-only.
- Пользовательский текст выводить с экранированием; не рендерить инструкции как доверенный HTML.
- Ограничить частоту регистрации, входа и операций создания; конкретные пороги уточняются.

### Развёртывание

- Не пересылать произвольный Docker JSON из браузера.
- Образ, mounts, privileges, network modes и лимиты задаёт доверенный шаблон.
- Не принимать `owner_id`, `image`, `gateway_url`, `privileged`, `mounts` и обязательные tool policies из пользовательских настроек.
- Docker socket и управляющие ключи не подключать пользовательским контейнерам.
- Адрес экземпляра получать из внутреннего реестра, а не из переданного пользователем URL.
- Отдельно оценить SSRF в функциях загрузки и проверки подключений; ограничивать сетевую достижимость управляющих сервисов.
- Не считать localhost источником доверенной личности.

### Изоляция

- Личные хранилища не подключаются чужим экземплярам.
- Одна общая bridge-сеть не считается доказательством межпользовательской изоляции.
- Лимиты ресурсов действуют и для уже работающих экземпляров.
- Контейнер не является доказательством невозможности эскалации или выхода.
- Не ограничивать все полезные функции автоматически: состав инструментов и прав определяется задачами стенда.

## Принятые решения и оставшиеся открытые пункты

- OpenClaw baseline: `7c12438929e5d198616fe8f602d896e011647d39`; отчёт пользователя для `2afe2b5` подтверждает два контейнера healthy, реальные XFS write/quota, remove/purge тестового набора и отдельные API/idempotency проверки. Gateway в браузер и модель не подключены.
- Основа веба: Open WebUI v0.12.5-slim, дополнительная страница/API; host-supervisor — opt-in. Основной lifecycle функционально принят на лабораторной ВМ.
- Один активный экземпляр на владельца принят; multiple instances per owner не поддерживаются.
- Поля draft: name/instructions. Изменения после создания пока остаются draft и не применяются к OpenClaw.
- Порог 50% по RAM/средней CPU принят; окно CPU 60 секунд и свежесть 10 секунд. Переносимый конечный budget и резервы модели должны быть заданы отдельно.
- На лабораторной ВМ report указывает 2 GiB RAM, 1 vCPU, 256 PIDs и XFS quota 10 GiB для экземпляра. EDQUOT, полный охват записи и disk budget на конечной машине остаются открытыми.
- `remove-retain` и `purge` на disposable test set подтверждены пользователем на ВМ для `2afe2b5`. В локальном коде есть owner-scoped restore того же ID/storage/quota и workspace-only file browser для list/preview/download. Ни restore, ни новые файловые routes не были на ВМ приняты. Просмотр ограничен рабочей папкой; остальные state/secrets не выдаются. Частично подготовленный failed-create cleanup требует отдельной проверки.
- Совместная/раздельная история веба и Telegram открыта; Telegram/LLM ещё не реализованы.
- Секреты не сохранять в репозитории/логах. Состав платформенных событий не включает обнаружение или автоматическое реагирование.

Функциональная приёмка и её пределы — `docs/verification.md`; дальнейший порядок — `docs/ROADMAP.md`.

## Критерии первой рабочей версии веба

- Настоящая регистрация и вход, а не локальное переключение тестовых пользователей.
- Пользователь видит только свои настройки/экземпляры; direct API attack на чужой runtime остаётся отдельной непроверенной ВМ-проверкой.
- Запрещённые инфраструктурные поля отклоняются сервером.
- Недоступность Docker/supervisor/LLM отображается честно; не выдавать фиктивный running/health или имитированный ответ модели.
- Основной lifecycle подтверждён реальным запуском на ВМ в объёме пользовательского отчёта; ограничения и непроверенное перечислены явно.
