# Передача проекта в новую сессию

## 1. Главная задача и статус

Завершить стадию 3 **работающим пользовательским сценарием**, а не новым набором изолированных модулей или десятками unit-тестов: кабинет → свой экземпляр → фактическое состояние → stop/start/restart → удаление контейнера с сохранением данных.

**Стадия 3 не принята окончательно.** Код сквозной связки написан, но последние исправления восстановления не проверены исполнением. Реальный новый runtime на Linux/XFS/Docker ВМ по доступным свидетельствам ещё не принят. Название commit `stage v3 3/3` не является доказательством завершённой проверки.

Стадии 1 и 2 уже приняты пользователем на ВМ. Не обнулять их из-за отсутствия Docker на Windows и не повторять их проверки без конкретной причины.

## 3. Замысел и уже принятые решения

Тема диплома: «Разработка прототипа среды функционирования программного обеспечения, использующего технологии искусственного интеллекта, с учетом требований ИБ».

Практика: открытая регистрация Open WebUI, персональный OpenClaw на владельца, раздельные данные и управление через кабинет. Пользователь и агент не получают Docker API, управляющие credentials или возможность ослаблять обязательные ограничения. В дальнейшем — общая модель на сервере и собственный Telegram-бот пользователя.

Основные решения:

- Первый Open WebUI аккаунт — admin, последующие — user; регистрация без ручного одобрения.
- Один не удалённый экземпляр на владельца, включая остановленный.
- Порог RAM/средней CPU **50% — единое правило проекта**. В `final` отказ, в `lab` — `would_deny`. Не превращать его в произвольный пользовательский/host override и не распространять автоматически на диск.
- Метрики CPU: окно 60 секунд, свежесть 10 секунд; swap не добавляется в физическую RAM.
- Удаление сейчас реализовано только как **remove с сохранением данных**. Purge и повторное подключение retained storage не реализованы; не удалять данные автоматически.
- Модели пока нет. Работа контейнера не означает работающий LLM-чат.
- Не объявлять проект соответствующим КИИ/ГИС/ИСПДН: нормативные идеи адаптируются, применимость отдельно обосновывается.

## 6. Текущая архитектура и карта кода

```text
Браузер /agent
  → Open WebUI: upstream human JWT + owner-scoped API
  → SupervisorClient: приватный AF_UNIX + отдельный service bearer
  → root Linux supervisor
      → RuntimeStore: intents, бюджеты, snapshot, replay
      → /proc + statvfs metrics
      → XfsVolumes: project ID, inheritance, block/inode hard limits
      → DockerEngine: create/start/stop/restart/remove + фактический inspect
```

| Файлы | Назначение |
| --- | --- |
| `control_plane/api.py`, `openwebui.py` | Проверенный upstream actor, draft/revision, lifecycle bridge. Клиент не задаёт actor/image/mounts. |
| `control_plane/runtime.py` | Ограниченный приватный клиент; credential только на backend, allowlist ответа. |
| `web/agent/app.js`, `ui-state.mjs`, `index.html` | Кнопки lifecycle, состояние, восстановление pending create и клиентские ключи. |
| `supervisor/service.py` | Root Linux service; `/v1/me`, `/v1/actions`, `/v1/replay`; явный запуск с `--enable-host-runtime`. |
| `supervisor/runtime_store.py` | Новый durable runtime-журнал: owner slot, бюджеты, неизменяемые snapshots, tombstones/retained disk. |
| `supervisor/metrics.py` | Фоновый сбор /proc/stat, MemTotal/MemAvailable, statvfs, прогрев CPU 60 секунд. |
| `supervisor/volumes.py` | XFS prepare/verify, private state DB вне тома, уникальные project IDs, проверка дерева/лимитов. |
| `supervisor/docker_engine.py` | Stdlib Docker HTTP Unix socket, API v1.45, immutable local image, проверка фактического контейнера. |
| `supervisor/seccomp.json`, `SECCOMP_SOURCE.md`, `MOBY_LICENSE`, `MOBY_NOTICE` | Default-deny профиль на базе закреплённого Moby с ограничением ioctl и альтернативных quota setters. |
| `supervisor/config.py`, `policy.py`, `storage.py`, `probes.py` | Профиль, ресурсная политика, read-only backend preflight, bounded subprocess. |
| `supervisor/registry.py`, `coordinator.py` | Предшествующее библиотечное ядро. Новый сервис использует RuntimeStore, а не неявно мигрированные старые reservations. |
| `scripts/configure_supervisor.py` | Явная подготовка root-owned deployment/runtime JSON, фиксация локального image ID. Не запускает службу и не назначает квоты. |
| `compose.supervisor.yaml` | Opt-in bridge: socket directory + credential read-only. **Без Docker socket в вебе.** |
| `scripts/smoke_runtime.py` | Один локальный сквозной сценарий с настоящими HTTP/SQLite и fake Docker/XFS/metrics. |

Базовый `compose.yaml` остаётся web-only. Без opt-in bridge API честно возвращает runtime_not_connected.

### Важные границы реализации

- Intent сначала атомарно резервирует слот/ресурсы и разрешает **только подготовку storage**. Для этого допускается отсутствие единственного признака `disk_quota_verified`; это не разрешение создавать/запускать контейнер.
- После реального назначения и readback персональной квоты выполняется полный свежий admission. Общие Accounting/Enforcement ON или валидный JSON не равны персональной квоте.
- RuntimeStore фиксирует полный профиль для своего журнала. Не удалять DB ради смены binding; автоматическая миграция профиля не реализована.
- Retained disk остаётся в бюджете после удаления. RAM/CPU освобождаются после подтверждённого remove.
- Контейнер: UID/GID 1000, readonly rootfs, cap_drop ALL, no-new-privileges, RAM/CPU/PIDs, bounded tmpfs, logging none, **network none**. Две bind-привязки state/secrets внутри одного XFS проекта.
- Disk limit должен делиться на 1024; inode hard limit — технический `max(1024, disk_bytes//4096)`, не пользовательская настройка.
- Одного cap_drop недостаточно для project inheritance: seccomp ограничивает filesystem ioctl/setattr и альтернативные пути. Совместимость на целевой ВМ ещё не подтверждена.
- `initialize_files` использует принятый lab bootstrap: gateway local/lan, token auth, loopback controlUi.allowedOrigins. Subsequent draft saves пока не применяются к уже созданному агенту.
- Root-owned административный snapshot нужен вне user-writable checkout. Служба проверяет владельца/предков; напрямую подставлять старый user-owned deployment.local.json в runtime config нельзя.

## 7. Что действительно проверено, а что нет

### Выполнено до последних исправлений

- Реально прошёл `scripts/smoke_runtime.py`: web → служебный HTTP → RuntimeApplication → SQLite, create/stop/start/restart/remove-retain, replay, второй владелец и retained budget.
- В этом прогоне Docker/XFS/метрики **имитированы**, служебный transport заменён на loopback TCP только внутри smoke. Реальный production transport — AF_UNIX.
- Прошли существующие веб-проверки; выполнялись JS syntax/существующие JS-тесты, compileall, git diff --check на тогдашних snapshots.
- Временные сервер и DB smoke были завершены/удалены.

### Последнее независимое ручное ревью и внесённые после него правки

Ревью не дало финального одобрения: найдены три ошибки. Затем код изменён:

1. Старый create-key после удаления: клиент отслеживает поколение экземпляра, сбрасывает старые ключи только при достоверной смене/удалении, не при unavailable. Есть memory fallback без sessionStorage и обработка instance_retired.
2. Replay при новом черновике: приватный `/v1/replay` загружает сохранённый **owner-scoped** request до проверки текущего draft. Новый неизвестный stale-запрос всё равно отклоняется. Браузеру не возвращается содержимое старого settings snapshot.
3. Восстановление из другой вкладки/после смены draft: service сообщает владельцу `pending_create_key` / `pending_create_revision`, кабинет предлагает «Продолжить создание» по исходному snapshot.
4. `paused` / `restarting` больше не подменяются `failed`; Docker adapter обрабатывает unpause внутри авторизованного lifecycle, reconciliation может проверять квоту этих состояний.

**Последние правки подтверждены чтением кода и применением патчей, но НЕ повторным исполнением.** Старые зелёные результаты не распространять автоматически на текущий snapshot.

### Не выполнено

- Обновление и итоговый прогон smoke после этих исправлений.
- Проверка актуального браузерного восстановления ключей/ревизий.
- Настоящий запуск pinned image с новым readonly/seccomp bootstrap.
- Проверка фактического Docker inspect против wanted projection, daemon support/cgroups/seccomp.
- Настоящие XFS assignment/readback, персональный EDQUOT и kernel enforcement именно нового runtime.
- Реальная служебная связка Unix socket/token permissions и upstream auth/proxy/Origin в новой конфигурации на ВМ.
- LLM, чат с Gateway, Telegram, purge, миграция/повторное подключение retained data, автозапуск службы.

## 8. Разрешения и известные блокировки

Текущий запрос на создание этой передачи контекста — **только документация**, не согласие запускать тесты, сервисы или менять ВМ.

В предыдущей работе отдельные операции не получили согласия: инструмент сообщал о withdrawn/timeout/no consent. В частности, было заблокировано обновление `scripts/smoke_runtime.py` для проверки нового draft/replay. Оно **не выполнено**, исходный smoke всё ещё использует revision=1 и не содержит нового сценария смены черновика. В новой сессии запросить явное разрешение на его актуализацию и один локальный прогон. Не считать перенос сессии сбросом запрета и не обходить его другим инструментом/агентом/переформулированной командой.

Также не получили полного исполнения отдельные завершающие проверки Docker adapter и автоматические scan/hash-review. Не выдавать их за успешные. Последующий выполненный HTTP/SQLite smoke проверял другой уровень с fake adapters, а не реальный Docker client.

`hermes verify` на этом Windows-хосте упирался в отсутствующий Docker (`docker compose build`). Не запускать его снова без изменения предпосылок и не повторять одинаковое сообщение о блокере после каждого внутреннего уведомления. Отсутствие Docker не является диагностированной ошибкой приложения и не отменяет приёмку ВМ старых стадий.

Без отдельного согласия: никаких установок/зависимостей, SSH, публикации, изменений fstab/mount/ФС, назначения квот, удаления/миграции данных, запуска привилегированного supervisor. Команды в документации — инструкции оператору, **не уже выданное согласие и не свидетельство выполнения**. Секреты/локальные credentials не читать без необходимости, не печатать, не сохранять в handoff и не отправлять наружу.

## 9. Следующие действия — конечный короткий маршрут

1. Прочитать эту передачу, сверить актуальный Git и реальные исходники. Не переписывать архитектуру и не добавлять новые слои ради абстракций.
2. Согласовать заблокированные шаги: актуализацию **одного** `scripts/smoke_runtime.py` и его локальный прогон без Docker/SSH/изменений ВМ. До согласия — только разрешённое чтение/обсуждение.
3. В этом же сценарии проверить прежний lifecycle и ровно существенные исправления: old key/revision после нового draft; отказ новому stale-запросу; recovery pending create; новое создание после remove; правдивые состояния. UI-generation требует проверки реального JS, а не только fake Python backend. Не заявлять результат, который сценарий не охватывает.
4. Если есть дефект — исправить конкретно его и перепроверить тот же маршрут. Не расширять задачу десятками мелких unit-тестов. Существующие тесты не удалять ради уменьшения количества.
5. После локальной проверки подготовить согласованную доставку на ВМ; общие бюджеты подтвердить, не превращать пример в принятую конфигурацию. Руководство — `docs/SUPERVISOR_RUN.md`.
6. После отдельного разрешения оператор выполняет setup/start: root-owned snapshot, `--enable-host-runtime`, opt-in Compose bridge. Помощник не делает это автоматически.
7. Одна функциональная приёмка на ВМ: создать из кабинета → настоящий running/health → stop/start и повтор без второго контейнера → второй аккаунт не видит чужой экземпляр → remove сохраняет данные/бюджет. Отдельно честно отметить результат индивидуальной квоты, не приравнивая readback к EDQUOT-испытанию.
8. Только по проверенным результатам закрыть стадию 3. Затем согласовать модель/чат/Telegram; не подмешивать их в текущую приёмку.

Пользователь прямо попросил меньше unit-тестов и больше работающего приложения. Отчёт начинать с пользовательской функции, изменений и конкретного непроверенного; не с количества тестов и не с очередного бесконечного плана.
