# Purge: immutable-конфигурация

## Статус

Реализация подключена локально к `XfsVolumes.purge`; замечания независимого source review по частичному созданию и повторам исправлены, финальная проверка quota-предиката блокеров не выявила. Это **не приёмка Linux/XFS**. Reboot и Ollama route acceptance этим изменением не закрываются.

Последний локальный прогон: 349 Supervisor-тестов (8 skipped), 100 основных; `compileall` и `git diff --check` — OK. В отдельном модуле managed-config purge проходят 15 тестов, использующих synthetic POSIX/ioctl adapters и реальную временную SQLite. `hermes verify --json` остановился на `docker compose build`: Docker CLI отсутствует, последующие boot/readiness-фазы не выполнялись.

## Граница и последовательность

- `RuntimeService.action` держит общую lifecycle-блокировку, проверяет отсутствие **Gateway и Sidecar** через `assert_purge_runtime_absent` и только после этого вызывает хранилище. Ошибка наблюдения блокирует удаление.
- Storage flock и root-owned база сериализуют операции хранилища. Root/Docker-администратор входит в доверенную зону и не должен независимо менять контейнеры, mountpoints или дерево данных во время purge; блокировка Supervisor не может остановить его Docker CLI. См. `DEPLOYMENT_CONFIG.md`.
- В существующей storage DB добавляются `volume_purge_configs` и `volume_purge_origins`: вторая сохраняет исходную стадию подготовки атомарно с переходом в `purging`, чтобы прерывание не теряло отличие ещё не подготовленного `reserved`-проекта. Файл базы открывается только в режиме `rw`, отсутствующая база не создаётся ради purge. Журнал связывает экземпляр и project ID с device/inode корня, state и файла (или фиксирует его отсутствие). Перед ioctl выполняется отдельный commit с `synchronous=FULL`.
- Для фиксированного `state/openclaw.json` используются no-follow directory FD, проверка записи `volume_directories`, владельцев/mode, single-link regular file, устройства и mount ID. Только root:1000/0440 файл в готовом state может получить снятие immutable. Legacy uid1000:gid1000/0600 и незавершённые root:root/0600 или root:1000/0600 остаются на обычном пути очистки **без ioctl**. Прерванное создание state с ещё root:root владельцем допускается только при сохранённой стадии каталога `created`; смена владельца готового каталога не принимается за такую стадию.
- После снятия бита проверяются read-back и идентичность имени, синхронизируется inode, удаляется ровно этот файл и синхронизируется state. При повторе допускается тот же journaled inode или уже отсутствующий файл после предыдущего unlink. Подмена inode не принимается за новый объект для снятия флага.
- Далее работает прежняя очистка дерева и проверка XFS project/quota. Журнал удаляется с остальными storage-записями только после завершения. Ошибка не освобождает квоту; RuntimeStore освобождает reservation лишь после storage success и собственных scrub/checkpoint-проверок.

Purge необратим: сбой может оставить частично удалённые данные своего экземпляра. Журнал гарантирует ограничение повтора и удержание квоты, а не откат удалённых данных или forensic secure erase.

Для journaled `reserved`-корня нулевые soft/hard limits до очистки не означают нулевой usage: назначенный проект уже может учитывать inode корня. Такой корень очищается по подтверждённой идентичности; финальное требование нулевого usage перед quota reset/release сохраняется.

Миграция не угадывает исходную стадию для старых строк `purging`, созданных до появления `volume_purge_origins`. Если старое прерывание оставило неоднозначный неподготовленный проект, операция остаётся fail-closed и требует отдельно согласованного административного восстановления. Записи рабочей базы автоматически не исправлялись.

## Локальная проверка

`supervisor/tests/test_managed_config_purge.py` использует реальные временные файлы/SQLite и явно синтетические POSIX FD, ownership/mount и immutable-операции. Проверены успешный путь, ошибки до/после flag clear, inode fsync, unlink и directory fsync, прерывание до обычной очистки, повтор после unlink, подмена inode, symlink/hardlink/FIFO, неверные метаданные/устройство/mount ID, legacy config без ioctl.

Portable generic-cleanup fixtures в старых тестах исключают только новый POSIX-этап: его поведение проверяется отдельным адаптером, а не выдаётся за настоящий ioctl.

## Ещё требуется отдельная приёмка Linux/XFS

Только после отдельного согласия, на disposable synthetic dataset, не на рабочем агенте:

1. Реальный create → remove с сохранением данных → purge с `FS_IMMUTABLE_FL`, отсутствие обоих контейнеров, исчезновение только своего каталога и освобождение project quota/reservation.
2. Прерывания процесса после journal commit, flag clear, inode fsync, unlink, directory fsync, частичной очистки дерева и quota cleanup; повтор с сохранением точных identity. Это требует crash/power-loss проверки, не только исключений Python.
3. Настоящие no-follow/ownership/mount/ссылочные негативные случаи, ошибки ioctl и read-back; квота при неуспехе остаётся зарезервированной, другие файлы не получают снятия флагов.
4. Повтор purge после полного storage cleanup и до RuntimeStore scrub/checkpoint; старые completed replay не повторяют удаление.

Никаких реальных Linux/XFS, quota, Docker или GPU-серверных действий при локальной разработке не выполнялось.
