## Целевой результат

Единый сервис: самостоятельная регистрация → вход → личный кабинет → создание персонального экземпляра OpenClaw → работа с ним из браузера → разрешённые настройки и управление → выход.

Пользователь управляет своим агентом, но не обязательной политикой платформы, чужими данными или Docker daemon. Сохранение формы, запущенный контейнер, готовность Gateway, наличие модели и работа канала — разные состояния.

## Правила исполнения

- Разработка в локальном Git-проекте, доставка через GitHub, clone/pull и сборка на ВМ. Публикация новых изменений — только после разрешения; этот план сам по себе не разрешает push, SSH или установки.
- Новые зависимости и образы для фактической установки/загрузки согласовать отдельно с объяснением назначения и места. Не устанавливать Docker на основной хост ради обхода ограничений.
- Не переписывать регистрацию и криптографию Open WebUI без отдельного решения. Сохранять его брендинг и лицензионные условия.
- До изменения кода каждого поведения писать и запускать тест; затем реализация и регрессия. Настоящую интеграцию проверять на ВМ, не подменять fake backend или декоративными статусами.
- Не включать все будущие функции в один большой релиз: каждый этап заканчивается проверяемым пользовательским результатом и перечнем оставшихся ограничений.
- Не записывать в репозиторий секреты, пользовательские данные или необезличенные диагностические материалы.

## Этап 4. Жизненный цикл экземпляра из кабинета

**Статус: базовый жизненный цикл пройден на ВМ по тому же пользовательскому отчёту для `4494d757`. Последующий локальный код не проверен на ВМ.** На одном контейнере выполнены create → stop → start → restart с последующим `running/healthy`; файлы и XFS project inheritance сохранены. Remove удаляет контейнер с сохранением данных и дискового резерва; после него выполнено новое создание с другим Project ID.

Обычный `remove` сохраняет данные. Owner-scoped explicit `purge` в текущей локальной версии открывает существующую storage SQLite для записи без создания базы, очищает только descriptor-anchored tree, сбрасывает квоту, scrub-ит runtime snapshot/token и payload всех операций экземпляра до освобождения резерва. Минимальные метаданные purge позволяют повтор после неуспешного WAL checkpoint. Тесты на временной SQLite и синтетических failure points прошли; настоящие Linux dirfd/XFS/Docker и ВМ не проверялись. Retained storage не переподключается, automatic purge отсутствует; cleanup storage при failed create отдельно не принимался.

**Оставшиеся проверки этапа 4 на текущем коде:** реальный browser end-to-end, проверка lifecycle и owner isolation на актуальной ВМ, конкурентные действия, восстановление supervisor при существующем runtime. Локальный fake HTTP/SQLite smoke проверяет точный replay, stale отказ и чужой purge, но не является VM/browser проверкой.

Базовый функциональный критерий «создать, управлять фактическим контейнером, сохранить данные при remove» пройден для версии `4494d757` по отчёту пользователя. Для текущей локальной версии перечисленные проверки и повторная VM-приёмка остаются открытыми.

**Подтверждённый порядок rollout на лабораторной ВМ:** старый supervisor `336aedde` удалил неисправный контейнер через кабинет с сохранением данных; пользователь проверил `docker ps -a` и SQLite `(0, 'removed')`, затем остановил старый supervisor и запустил новый `4494d757` с сохранёнными runtime.json/SQLite. После этого новый контейнер прошёл healthcheck. Значит, startup reconciliation не принимал старый seccomp binding: контейнера уже не было, owner slot был неактивен. Это подтверждает этот порядок на данной ВМ, но не запуск новой версии поверх активного контейнера со старым профилем. См. `docs/verification.md`; данные и DB не очищать ради обновления.
