## Целевой результат

Единый сервис: самостоятельная регистрация → вход → личный кабинет → создание персонального экземпляра OpenClaw → работа с ним из браузера → разрешённые настройки и управление → выход.

Пользователь управляет своим агентом, но не обязательной политикой платформы, чужими данными или Docker daemon. Сохранение формы, запущенный контейнер, готовность Gateway, наличие модели и работа канала — разные состояния.

## Правила исполнения

- Разработка в локальном Git-проекте, доставка через GitHub, clone/pull и сборка на ВМ. Публикация новых изменений — только после разрешения; этот план сам по себе не разрешает push, SSH или установки.
- Новые зависимости и образы для фактической установки/загрузки согласовать отдельно с объяснением назначения и места. Не устанавливать Docker на основной хост ради обхода ограничений.
- Не переписывать регистрацию и криптографию Open WebUI без отдельного решения. Сохранять его брендинг и лицензионные условия.
- До изменения кода каждого поведения писать и запускать тест; затем реализация и регрессия. Настоящую интеграцию проверять на ВМ, не подменять fake backend или декоративными статусами.
- Не включать все будущие функции в один большой релиз: каждый этап заканчивается проверяемым пользовательским результатом и перечнем оставшихся ограничений.
- Не записывать в репозиторий секреты, пользовательские данные или необезличенные диагностические материалы.

## Этап 3. Спроектировать границу управления и правила допуска

До подключения кнопки «Создать» определить контракт и ограничения, а не делать веб прямым прокси Docker API.

- [ ] Отдельный доверенный supervisor/provisioner: веб не получает полный Docker socket, агент не получает управляющие ключи или API daemon.
- [ ] Определить проверяемую служебную авторизацию веба перед supervisor и передачу идентичности; не доверять произвольному заголовку user-id.
- [ ] Серверный реестр: владелец, platform instance ID, фактический container ID, версия шаблона, состояния операций и отдельные хранилища. Имена контейнеров не заменяют авторизацию.
- [ ] Закрытый набор операций и параметров. Образ, mounts, capabilities, namespaces, сеть и лимиты задаёт шаблон; клиентский Docker JSON не принимается.
- [ ] Определить идемпотентность повторных запросов, конкурентные операции и восстановление после сбоя между записью в БД и созданием контейнера.
- [ ] Согласовать число экземпляров на пользователя и конкретные разрешённые настройки.
- [ ] Определить смысл порога 50%: ресурсы, окна измерения, резерв нового экземпляра, конкурентные создания и поведение при недоступных метриках. Не обещать полную защиту от DoS.
- [ ] Определить квоты работающего экземпляра: CPU, RAM, процессы, диск и необходимые сетевые ограничения.
- [ ] Согласовать судьбу данных при удалении. Не уничтожать volume неявно вместе с контейнером.

**Приёмка:** контракт и шаблон описаны в проекте, значимые открытые решения согласованы, тесты отказов и гонок спроектированы. Запрос пользователя не может расширить обязательную политику.

## Этап 4. Реализовать настоящий жизненный цикл из кабинета

- [ ] Создание экземпляра по шаблону и серверная привязка владельца.
- [ ] Истинные состояния: операция выполняется, контейнер создан/запущен/остановлен, Gateway готов/не готов, ошибка. Не ограничиваться выдуманным running после нажатия кнопки.
- [ ] Запуск, остановка, перезапуск и удаление по согласованной политике данных.
- [ ] Обработка повторного клика, двух параллельных запросов, нехватки ресурсов и таймаута supervisor.
- [ ] Сверка реестра с Docker после перезапуска управляющего компонента; обработка потерянных/частично созданных экземпляров.
- [ ] Журнал операций без токенов и содержимого личной переписки.
- [ ] Проверки двух пользователей: чужой instance ID, перечисление, управление, журналы, конфигурация и данные недоступны.

**Приёмка:** «Создать» действительно создаёт реальный принадлежащий пользователю контейнер. Статус подтверждается состоянием платформы и Docker; ошибка не выдаётся за успех.

## Этап 5. Подключить Gateway и применение настроек

- [ ] Разрешённые пользовательские поля преобразуются в конфигурацию выбранной версии OpenClaw; обязательные ограничения не редактируются через эту форму.
- [ ] Обновление конфигурации имеет отдельные состояния «сохранено» и «применено», с понятной ошибкой при отказе.
- [ ] Адрес и идентичность Gateway берутся из реестра, не из URL пользователя.
- [ ] Соединение backend → Gateway с корректными pairing, origin и полномочиями. Не проксировать все административные RPC без фильтрации.
- [ ] Маршрутизация браузерной сессии к своему экземпляру; переподключение и серверная проверка владельца.
- [ ] Проверки файловой и сетевой изоляции; отдельные контейнеры сами по себе её не доказывают.

**Приёмка:** настройки реально применяются к своему OpenClaw; состояние Gateway читается из настоящего соединения. Без модели полноценный ответ агента ещё не считается рабочим.

**Приёмка:** реальные сообщения и действия проходят через нужный агентный экземпляр. Сохранённый токен не считается работающим каналом.
